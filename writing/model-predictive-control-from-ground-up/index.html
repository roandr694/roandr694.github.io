Model Predictive Control: predict, optimize, and replan

Building MPC from dynamics, costs, and constraints, with worked examples and a disturbed point-mass simulation showing receding-horizon feedback.

I find Model Predictive Control easier to understand as a repeated calculation. Start from an estimate of where the robot is now. Predict how it would move under several future commands. Choose a sequence that makes progress while respecting the model and limits. Execute the first command, measure again, and solve a new problem.

The interesting part is how that repeated calculation becomes feedback. The controller has a plan, but its next decision starts from the state the robot actually reached. I want to build up the optimization problem carefully, then use a small simulation to see what changes when a disturbance makes the original prediction wrong.

A model that predicts motion

A state is a collection of variables sufficient to describe the dynamics under the chosen model. For a point mass moving along a line, I can use position ppp and velocity vvv:

xt=[ptvt].x_t=\begin{bmatrix}p_t\\v_t\end{bmatrix}.xt​=[pt​vt​​].

The input utu_tut​ will be acceleration. If acceleration is constant during a control interval of duration Δt\Delta tΔt, the discrete model is

pt+1=pt+vtΔt+12utΔt2,vt+1=vt+utΔt.p_{t+1}=p_t+v_t\Delta t+\tfrac12u_t\Delta t^2, \qquad v_{t+1}=v_t+u_t\Delta t.pt+1​=pt​+vt​Δt+21​ut​Δt2,vt+1​=vt​+ut​Δt.

This is the exact integration of this simple continuous-time model over that interval. A different integration convention can give different coefficients. If the input were force, the acceleration would additionally depend on mass.

A numerical example: with pt=0p_t=0pt​=0, vt=1v_t=1vt​=1 m/s, ut=−1u_t=-1ut​=−1 m/s², and Δt=0.2\Delta t=0.2Δt=0.2 s, the next position is 0.180.180.18 m and the next velocity is 0.80.80.8 m/s. Braking changes where the robot goes during the interval as well as its velocity afterward.

xt+1=Axt+But,A=[1Δt01],B=[12Δt2Δt].x_{t+1}=Ax_t+Bu_t, \qquad A=\begin{bmatrix}1&\Delta t\\0&1\end{bmatrix}, \quad B=\begin{bmatrix}\tfrac12\Delta t^2\\\Delta t\end{bmatrix}.xt+1​=Axt​+But​,A=[10​Δt1​],B=[21​Δt2Δt​].

Predicting several steps ahead

At the current robot time ttt, let xk∣tx_{k\mid t}xk∣t​ mean the predicted state kkk steps into the future. The bar means that the prediction is being made at time $t$; it is not division.

The prediction begins from an estimated current state:

x0∣t=x^t,xk+1∣t=f(xk∣t,uk∣t).x_{0\mid t}=\hat x_t, \qquad x_{k+1\mid t}=f(x_{k\mid t},u_{k\mid t}).x0∣t​=x^t​,xk+1∣t​=f(xk∣t​,uk∣t​).

The hat marks an estimate. Position may come from a sensor, while velocity may be estimated from several measurements and a motion model. In the simulation below, I assume the full state is known exactly so I can isolate the replanning behavior.

A prediction horizon of NNN steps contains NNN input commands and N+1N+1N+1 states including the initial state. Its duration is NΔtN\Delta tNΔt. For N=20N=20N=20 and Δt=0.2\Delta t=0.2Δt=0.2 s, the controller looks four seconds ahead.

For the linear model, the first two predictions are

x1∣t=Ax^t+Bu0∣t,x_{1\mid t}=A\hat x_t+Bu_{0\mid t},x1∣t​=Ax^t​+Bu0∣t​, x2∣t=A2x^t+ABu0∣t+Bu1∣t.x_{2\mid t}=A^2\hat x_t+ABu_{0\mid t}+Bu_{1\mid t}.x2∣t​=A2x^t​+ABu0∣t​+Bu1∣t​.

The second equation makes the coupling visible: the first command affects multiple future states. An acceleration that reduces today's position error can also create velocity that must be removed later.

Specifying what the controller should prefer

Prediction alone does not say which motion is useful. I need a cost: a numerical way to compare candidate motions. Lower cost means more desirable under the choices I put into the objective.

For a reference state xrefx_{\rm ref}xref​ and reference input urefu_{\rm ref}uref​, a common stage cost is

A terminal cost Vf(xN∣t)V_f(x_{N\mid t})Vf​(xN∣t​) evaluates the final predicted state. A velocity penalty at the end discourages finishing the prediction close to the target but still moving quickly.

The finite-horizon optimization problem

A nominal controller predicts a single trajectory using its chosen model, without explicitly optimizing over a set of possible model errors. One standard nominal MPC problem is

min⁡x0:N∣t, u0:N−1∣t∑k=0N−1ℓ(xk∣t,uk∣t)+Vf(xN∣t)subject tox0∣t=x^t,xk+1∣t=f(xk∣t,uk∣t),xk∣t∈X,uk∣t∈U,xN∣t∈Xfif a terminal set is imposed.\begin{aligned} \min_{x_{0:N\mid t},\,u_{0:N-1\mid t}}\quad &\sum_{k=0}^{N-1}\ell(x_{k\mid t},u_{k\mid t}) +V_f(x_{N\mid t})\\ \text{subject to}\quad &x_{0\mid t}=\hat x_t,\\ &x_{k+1\mid t}=f(x_{k\mid t},u_{k\mid t}),\\ &x_{k\mid t}\in\mathcal X,\quad u_{k\mid t}\in\mathcal U,\\ &x_{N\mid t}\in\mathcal X_f\quad\text{if a terminal set is imposed}. \end{aligned}x0:N∣t​,u0:N−1∣t​min​subject to​k=0∑N−1​ℓ(xk∣t​,uk∣t​)+Vf​(xN∣t​)x0∣t​=x^t​,xk+1∣t​=f(xk∣t​,uk∣t​),xk∣t​∈X,uk∣t​∈U,xN∣t​∈Xf​if a terminal set is imposed.​

The colon notation 0:N0:N0:N means the sequence from index zero through NNN. The decision variables are the numbers the optimizer is allowed to choose. The dynamics equations constrain predicted states to agree with the commands and the initial estimate.

The sets X\mathcal XX and U\mathcal UU describe allowed states and commands. A state bound may also be imposed at the terminal state; the exact indexing should be stated in an implementation. The optional terminal set Xf\mathcal X_fXf​ restricts where the plan can end.

A solver is the numerical algorithm used to find a solution. The star in u0∣t⋆u^\star_{0\mid t}u0∣t⋆​ denotes an optimized command. For a nonlinear problem, the available solution may be a local optimum or an approximate result, rather than a globally best plan.

The OSQP MPC example shows a concrete linear-quadratic formulation. My point-mass example uses its own model and weights, with a general numerical optimizer, rather than reproducing that example's quadcopter experiment.

Costs and constraints do different jobs

A penalty makes a behavior expensive. A hard constraint excludes it from the mathematical feasible set. Increasing an effort penalty does not enforce an exact acceleration limit.

For the longer point-mass simulation, I impose

−1≤uk∣t≤1 m/s2,−1≤vk∣t≤1 m/s,-1\leq u_{k\mid t}\leq1\ \text{m/s}^2, \qquad -1\leq v_{k\mid t}\leq1\ \text{m/s},−1≤uk∣t​≤1 m/s2,−1≤vk∣t​≤1 m/s,

along with predicted position bounds of −0.25-0.25−0.25 to 2.52.52.5 m. The optimizer must balance progress with these restrictions. It can accelerate, coast at the speed limit, and brake as approaching the reference becomes more important.

A soft constraint introduces a nonnegative slack variable that permits violation at a cost. For an upper position preference, one version is

pk∣t≤pmax⁡+sk,sk≥0,p_{k\mid t}\leq p_{\max}+s_k, \qquad s_k\geq0,pk∣t​≤pmax​+sk​,sk​≥0,

with an added penalty such as ρsk2\rho s_k^2ρsk2​. The slack measures how much the original bound is relaxed. A large finite penalty makes that relaxation unattractive, but does not turn the preference into a hard physical guarantee.

The predictions also represent the chosen model at selected times. Real constraint satisfaction additionally depends on estimation, model error, discretization, and execution. Checking collision clearance only at a few prediction nodes can miss a collision between them.

Executing the first command creates feedback

After solving for a whole sequence, standard receding-horizon MPC applies

ut=u0∣t⋆.u_t=u^\star_{0\mid t}.ut​=u0∣t⋆​.

At the next control step, it obtains a new estimate x^t+1\hat x_{t+1}x^t+1​ and solves again. The unused part of the old plan may help initialize the next solve, but it is not a commitment to execute those commands unchanged.

at each control update:
    estimate current state
    update references and relevant constraints
    solve the finite-horizon problem
    check solver result, feasibility, and deadline
    apply the first accepted command
    use the system's specified fallback if the solve is unusable

The fallback is an execution-system design choice. A command being numerically available does not mean it arrived in time or satisfied the acceptance checks.

This gives an implicit feedback policy: the current state changes the optimization problem, which changes the chosen first command. Even with a fixed dynamics model, MPC can therefore respond to disturbances. Replanning does not by itself mean the model is learning online.

Why horizon length and terminal design matter

A short horizon can make a future consequence invisible. At 1 m/s with at most 1 m/s² of braking, the ideal continuous-time stopping distance is

dstop=v22amax⁡=0.5 m.d_{\rm stop}=\frac{v^2}{2a_{\max}}=0.5\ \text{m}.dstop​=2amax​v2​=0.5 m.

That calculation assumes constant maximum deceleration and ignores delay. A prediction that ends too soon may undervalue braking unless its terminal design accounts for the remaining motion. Increasing NNN looks farther ahead, but also changes the computational problem. Decreasing the timestep while holding NNN fixed shortens the horizon in seconds.

A terminal cost can approximate the cost of continuing after the prediction ends. A terminal set can restrict the final state to a region where a suitable local controller can continue operating. These have distinct roles, and arbitrary terminal weights do not automatically prove stability.

Recursive feasibility means that, after taking an accepted step, the next optimization remains feasible. Stability concerns how the closed-loop state behaves over time, such as approaching an equilibrium. Both require assumptions and a controller design that supports the claim. Repeatedly obtaining a low finite-horizon cost is insufficient on its own.

The textbook Model Predictive Control: Theory, Computation, and Design, by Rawlings, Mayne and Diehl is a reference for this theory. The terminal weights in my toy simulation are illustrative choices, not a stability certificate.

Linear, nonlinear, and uncertain models

With linear dynamics, a cost built from nonnegatively weighted squares, and linear constraints, the problem can be a convex quadratic program. Convexity means that any local minimum is also global; it does not imply that numerical solvers have zero error or zero computation time.

For this class of problem, predicted states can be expressed as functions of the input sequence and the current state. Substituting those expressions into the objective leaves a quadratic problem in the commands. Alternatively, I can keep states and commands as variables and enforce the dynamics with equality constraints. Tedrake's trajectory-optimization notes explain these formulations.

Nonlinear MPC uses a nonlinear prediction model and can require iterative local optimization. Contact changes, friction, and the choice of which side of an obstacle to pass can make the problem more difficult. Even with linear motion dynamics, keeping a robot outside an obstacle generally creates a nonconvex allowed region.

Warm starting initializes a solve using a previous solution, often shifting the old sequence forward and appending a candidate final action. It can reduce numerical work. That initial guess still needs to be checked and improved; a shifted sequence is not automatically feasible under the new state and constraints.

Nominal MPC predicts one model trajectory. Robust formulations explicitly account for a specified uncertainty set, while stochastic formulations model uncertainty probabilistically. For example, a chance constraint bounds a modeled probability of violation. Any resulting claim depends on those uncertainty assumptions and on whether the bound concerns one event or an entire task.

How this connects to learned policies

A standard MPC controller solves an explicit dynamics-and-cost problem during execution. A behavior-cloned policy predicts actions from learned examples. Both produce commands, but the computations and evidence supporting them differ.

The Diffusion Policy post also uses receding-horizon execution: generate a sequence, execute a prefix, and observe again. That shared execution pattern does not imply that diffusion sampling solves the explicit model-based optimization problem written here.

MPC and learning can also be combined. A learned dynamics model can supply predictions, a learned value function can help with terminal cost, and an MPC controller can provide labels for imitation learning. In RL, reward-based training can learn a policy that avoids solving the same explicit planning problem at every step. Each combination introduces its own model, data, and computation tradeoffs.

For me, the useful way to read an MPC implementation is to identify the state estimate, dynamics, objective, constraints, horizon in seconds, and the command that actually reaches the system. Those choices explain the resulting behavior more directly than the name of the solver alone.
